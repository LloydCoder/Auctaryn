# Inter-Agent Security Contract

## Scope and authority

Auctaryn's in-process message bus provides an authenticated envelope contract for handoffs and agent-to-agent instructions. It is not itself a network transport. A real HTTP, queue or A2A/MCP transport must preserve the same verification, identity, expiry, replay and size checks.

Tinlance Agent Platform remains authoritative for managed agent identities, tenant binding, scoped tokens and delegation. The message bus requires a managed identity integration by default and requires a live token with `inter_agent:send` for sending and `inter_agent:receive` for receiving. The unbound mode is an explicit test-only option and must not be used in deployment. Cross-owner delivery is denied by default; it requires an explicit cross-tenant authorization callback.

## Envelope integrity

The HMAC-SHA-256 signature covers the canonical envelope: message ID, sender, recipient, payload, issue timestamp and expiry. Changing any of those fields invalidates the signature. Payloads must be finite JSON objects no larger than 64 KiB. Keys require 32–512 UTF-8 bytes and low-character-diversity secrets are rejected. This heuristic is not an entropy proof: production keys must be generated by a CSPRNG and provisioned through the authoritative platform or a managed key service. Agent IDs and message IDs are validated; keys are not returned by the message bus.

Messages expire within one hour (five minutes by default). Verification checks the recipient identity, token scope, time window, signature and replay state. A successful verification consumes the message ID once and removes the message from the inbox. Replays are rejected. The consumed-ID cache is bounded; at capacity, verification fails closed until expired entries can be pruned.

## Inbox and key lifecycle

Each recipient inbox is bounded to 1,000 messages, the aggregate queue is bounded to 1,024 messages, and the message identity registry is bounded to 10,000 agents. Expired messages are pruned before capacity checks and when reading the inbox. When a managed identity service is configured, inbox reads require a valid `inter_agent:receive` token for that recipient; verification requires the same scope. Inbox reads return copies so callers cannot mutate stored messages by reference.

Replacing a registered key requires an explicit rotation flag. Rotation clears pending messages from that sender so they cannot be verified under the new key. When a managed identity service is configured, new key registration and rotation require an injected key-management authorizer that returns an explicit boolean grant; absence, exceptions, or non-boolean grants deny the operation. In production, that callback must be backed by Tinlance Agent Platform or a managed secret/key service and emit an auditable key-lifecycle record. Current keys, inboxes and replay state are in memory and are not durable or multi-replica safe.

## Circuit-breaker containment

Circuit-breaker state is per agent, with bounded state and dependency registries. Dependency self-edges and cycles are rejected; traversal fails closed on a detected cycle. After cooldown, only one half-open probe is allowed at a time. A failed probe trips the breaker again; a successful probe closes it. A bounded probe timeout allows recovery if a probe never reports an outcome.

## Production integration gates

- Add a transport adapter with TLS, service authentication, bounded request bodies, queue acknowledgement semantics and tenant-bound routing.
- Bind each message to the authoritative identity/token context and ensure sender and recipient belong to the same permitted tenant or an explicitly authorized cross-tenant relationship.
- Persist keys, rotation history, replay IDs and message audit records in durable, access-controlled storage.
- Integrate delivery and consumption receipts with the platform's evidence and audit contract.
- Test queue redelivery, concurrent duplicate delivery, broker outage, key revocation and cross-tenant routing in the deployed transport.
